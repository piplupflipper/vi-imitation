## 1. 目的

Vim のキーバインドと編集機能を持つ、ターミナル用のモーダルエディタを新しく作る。
Vim と Neovim のコードと仕様は引き継がず、0 から設計する。
Vim との 100% の互換は目指さない。

このプロジェクトは、作者の Go の学習を兼ねる。
このため、動くものを早く作ることに加えて、Go の標準的な書き方と道具に沿うことを重視する。

### 1.1 引き継がない Vim の仕様

| 仕様 | 引き継がない理由 |
|---|---|
| Vimscript | 設定と拡張機能のためだけの独自言語であり、処理系の実装が大きい |
| `.vimrc`、`init.vim`、`init.lua` | Vimscript と Lua の処理系が前提になる |
| 約 350 項目のオプション | 本体を小さく保つ方針に反する |
| プラグインのマッピングがドットリピートで繰り返されない仕様 | 拡張機能の操作を、標準の操作と同じように繰り返せるようにする（FR-12） |
| `\v` や `\m` で意味が変わる正規表現の方言 | Go の標準ライブラリの正規表現を使う |
| 数字のレジスター（`0`〜`9`）と小さな削除のレジスター（`-`）。どれに入るかが、ヤンクか削除か、消した範囲が行をまたぐか、どのモーションか（`%` など）で決まる仕様 | 規則が覚えにくく、9 件では履歴として少ない。件数を設定できるレジスターの履歴（FR-51、FR-53）に置き換える |
| `"`、`.`、`:`、`+`、`*`、`/`、`%`、`#`、`=` のレジスター | 名前と働きの組を覚える負担に見合う使い道が少ない。`=` は Vimscript の式を前提にする。ホストのクリップボードは、名前を指定せずに履歴の先頭を送る（FR-56）。`_` だけは残す（FR-50） |
| `@:`（直前のコマンドラインを実行し直す） | 使う場面が少ない。コマンドラインの履歴で同じことができる。`@@` は直前に再生したマクロだけを繰り返すものになる（FR-57） |
| `@a` の後の `.` が、マクロの中の最後の変更を繰り返す仕様 | `.` でマクロ全体を繰り返すほうが直感に合う（FR-57） |
| ビジュアルモードの `p` が、置き換えられたテキストで無名のレジスターを上書きする仕様 | 同じテキストを何か所にも貼れない（FR-51） |
| ウィンドウ（`:split` など、エディタの中での画面の分割）と、画面の構成ごと切り替える Vim のタブページ | 画面の分割は端末多重化ソフトのペインに任せ、ペインごとに 1 つの client を動かす（FR-58、FR-66）。タブは client ごとのバッファの並びにする（FR-62） |
| 隠れたバッファ（Vim の `'hidden'`。画面に無いまま読み込んでおくバッファ） | バッファとタブを 1 対 1 にし、タブを閉じたらバッファも閉じる（FR-64） |
| エディタの中のターミナル（`:terminal`） | 外部のコマンドは `:!` で端末を渡して動かすか、端末多重化ソフトのペインとポップアップで動かす（FR-80、FR-168） |
| ノーマルモードの `<` と `>` にモーションを続けるオペレーター（`<j`、`>ip` など） | `<` と `>` だけで `<<` と `>>` と同じ操作にする（FR-76）。回数は行数として扱う |
| ノーマルモードの `<C-i>`（ジャンプリストを進む）の既定の割り当て | 端末では `<Tab>` と同じバイトであり、`<Tab>` をタブの移動に使う（FR-98）。設定で他のキーに割り当てれば使える |
| `'readonly'` と `'modifiable'` の 2 つのオプション | 編集の禁止という 1 つのバッファの状態にまとめる（FR-85） |
| ノーマルモードの `s`（1 文字を消して入力する） | `s` で始まるキーを囲みの操作に使う（FR-73〜FR-75）。既定では割り当てない。ビジュアルモードの `s`（選択を消して入力する）は残す |
| `K`（`'keywordprg'` で引く）、`gq`（`'textwidth'` で行を整える）、`<C-]>`（タグへ移る） | LSP の操作（ホバー、整形、定義へ移る）に割り当てる（FR-95）。nvim が LSP の有効なバッファで同じキーを LSP の操作にしているのに合わせる |

## 2. 用語

| 語 | 意味 |
|---|---|
| 本体 | エディタの実行ファイル `vi-imitation` と、そのプロセス |
| 拡張機能 | 本体とは別の実行ファイルとして配布し、本体が子プロセスとして起動するプログラム |
| 標準の拡張機能 | このリポジトリで開発し、本体と一緒に配布する拡張機能 |
| コンパイルする拡張機能 | Go で書き、コンパイルして実行ファイルにする拡張機能 |
| スクリプトの拡張機能 | 利用者が Go のソースファイルとして置き、Go のインタープリターである yaegi が実行する拡張機能 |
| オペレーター | `d`（削除）や `c`（変更）のように、後に続く範囲に対して行う操作 |
| モーション | `w`（次の単語）のように、カーソルの移動先を指定するコマンド |
| テキストオブジェクト | `iw`（単語の内側）のように、カーソル位置から範囲を指定するコマンド |
| ドットリピート | `.` キーで直前の編集を繰り返す機能 |
| RPC | 別のプロセスにある関数を、メッセージを送って呼び出す仕組み |
| バージョン番号 | バッファが変更されるたびに増える番号。拡張機能が古い内容をもとに計算した編集を、本体が見分けるために使う |
| 期限 | 本体が拡張機能の応答を待つ時間の上限 |
| LSP | Language Server Protocol。エディタと言語サーバーの間のプロトコル |
| DAP | Debug Adapter Protocol。エディタとデバッガーの間のプロトコル |
| MCP | Model Context Protocol。AI のアプリケーションと、ツールやデータを提供するサーバーの間のプロトコル |
| ACP | Agent Client Protocol。エディタとコーディングエージェントの間のプロトコル。同じ略称の Agent Communication Protocol は指さない |
| JSONC | JSON にコメントを書けるようにした形式 |
| server | 段階 3 で本体を分けたうちの、バッファ、レジスター、検索、マクロ、ドットリピート、拡張機能を持つ側のプロセス（FR-58） |
| client | 段階 3 で本体を分けたうちの、server に繋ぐ側のプロセス。編集の client、ポップアップの部品の client、ペインの部品の client、待つだけの client の 4 種類がある（4.6、FR-58） |
| 編集の client | client のうち、ペインで起動し、タブの行を持ってバッファを編集するもの。端末に描き、キーを受ける |
| 操作中の client | 編集の client のうち、最後にキーを受けたもの。部品の client で受けたキーは、その部品を開いた元の編集の client が受けたものとして数える（基本設計 1.2） |
| 端末多重化ソフト | 1 つの端末の中に複数の端末（ペイン）を並べるプログラム。この文書では tmux と herdr を指す |
| ペイン | 端末多重化ソフトが分割した、1 つの端末として振る舞う領域 |
| タブ | client が画面の上に並べる、バッファ 1 つ分の見出し。1 つのバッファは、どれか 1 つの client のタブになる（FR-62） |
| ポップアップ | 画面の上に浮かべて出す、操作できる窓（FR-68） |
| 表示の部品 | ポップアップとペインに出す、本体が描き方を持つ表示の単位。テキストのバッファ、一覧、木、入力の行がある（FR-72） |
| 編集の禁止 | バッファのテキストを変える操作をすべて断る、バッファごとの状態（FR-85、FR-118） |
| 提供者 | 本体の、プロトコルに依存しない操作（定義へ移動など）を、宣言ファイルで引き受けると名乗った拡張機能（FR-94） |

## 3. 対象とする範囲

### 3.1 対象

- ターミナルで動作するエディタ本体
- 拡張機能を起動、監視、呼び出すための仕組みと、拡張機能 API
- 標準の拡張機能（LSP、DAP、MCP、ACP、tree-sitter、スクリプトの実行。段階 3 で git 連携、markdown の描画、ツリー型のファイラ、ファジーファインダーを足す）
- 端末多重化ソフト tmux と herdr との連携（段階 3。ペインの分割、ポップアップ、フォーカスの移動）
- 拡張機能の取得、ビルド、更新、削除（段階 3）

### 3.2 対象外

- GUI
- tmux と herdr 以外の端末多重化ソフトとの連携。それ以外の端末多重化ソフトの中や、端末多重化ソフトの外では、server と client を 1 つのプロセスで動かす（FR-60）
- エディタの中のターミナル（Vim の `:terminal`）
- エディタの中での画面の分割（Vim のウィンドウ）
- 拡張機能が端末のセルを直接描くこと。拡張機能は表示の部品をデータで渡す（FR-72）。外部の TUI のプログラムは、端末多重化ソフトのポップアップか `:!` で動かす
- Vimscript、Lua、`.vimrc`、`init.vim`、`init.lua` の本体でのサポート
- Vim のオプションの体系と、Vim の正規表現の方言
- エディタ自身が言語モデルを直接呼び出す機能
- 悪意のある拡張機能から本体と利用者のデータを守ること（NFR-03 の注を参照）
- Linux 以外の OS での動作保証

`.vimrc` の `map` と `set` の一部を新しい設定形式へ変換する機能は、拡張機能として後から作る余地を残す。

## 4. 機能要件

### 4.1 編集

| ID | 要件 |
|---|---|
| FR-01 | ノーマル、インサート、ビジュアル、コマンドラインの各モードを持つ |
| FR-02 | ノーマルモードで、回数、オペレーター、モーションまたはテキストオブジェクトを組み合わせて編集を指定できる（例: `d2w`、`ci"`） |
| FR-03 | Vim の標準のモーション、オペレーター、テキストオブジェクトを本体が持つ。対象の一覧は実装の段階で定める。1.1 で引き継がないとしたもの（ノーマルモードの `<` と `>` のオペレーター、`s`）は持たない |
| FR-04 | レジスターを持つ。名前と働きは 4.5 による。段階 3 では server がレジスターを持ち、同じ server に繋いだ client の間で共有する（FR-58） |
| FR-05 | マクロを記録し、再生できる。マクロはキー入力の列として、テキストと同じ名前付きのレジスターに記録する。記録したマクロは、テキストとして貼って編集し、レジスターへ戻せる |
| FR-06 | ドットリピートを持つ。解釈済みの編集コマンドを 1 つの値として記録し、その値を再実行する |
| FR-07 | アンドゥとリドゥを持つ |
| FR-08 | Ex コマンドは `:w`、`:q`、`:s`、`:g` などの部分集合を持つ。対象の一覧は実装の段階で定める |
| FR-09 | 正規表現は Go の標準ライブラリ（`regexp`）の文法に従う |
| FR-144 | 本体の既定のキーのうち、ノーマルモードとビジュアルモードの英字 1 文字の大文字のキーは、同じモードの小文字のキーの操作の「向きを逆にしたもの」（`n` と `N`）、「単位を大きくしたもの」（`w` と `W`）、「行の端まで広げたもの」（`d` と `D`）のどれかにする。例外は `J`（行をつなげる）と `K`（ホバー。FR-95）だけである。既定のキーを足すときも、この方針に照らして決める |
| FR-145 | ノーマルモードの `U` は、`<C-r>` と同じリドゥである。回数は `<C-r>` と同じく繰り返す回数として扱う（`2U` は 2 回リドゥする）。`<C-r>` もリドゥのまま残す。ビジュアルモードの `U`（選択を大文字にする）は変えない |
| FR-146 | ノーマルモードの `Y` は、行末までヤンクする（`y$`）。回数は `D` と同じく `y$` の回数として扱う（`3Y` は `3y$`）。ビジュアルモードの `Y`（選んだ行をヤンクする）は変えない。`yy` に当たる本体の操作（`yank-line`）は既定のキーを持たずに残し、設定の `keymap` で `Y` に割り当てれば Vim の `Y` に戻せる（FR-126） |
| FR-153 | `/` と `?` でパターンを打っている間、打つたびに、カーソルから次の一致（回数を付けたときはその数だけ先の一致）を探し、画面をその一致へ動かして、一致に色を付ける。色の名前は `incsearch` とし、`colors` で変えられる。`search.highlight`（FR-137）が真なら、ほかの一致にも `search` の色を付ける。一致が無いとき、打っている途中のパターンが正規表現として正しくないときは、誤りを出さず、一致を出さずに画面を打つ前のままにする。打っている間の `<C-g>` と `<C-t>` は、出す一致を次と前の一致へ動かす（打ったパターンが空の間は何もしない）。`<CR>` で一致へ移って決め（移り先は、打っている間に出す一致と同じ規則で決める）、`<Esc>` と `<C-c>` で取り消すと、カーソルと画面を打つ前に戻す。ジャンプリスト、`n` が繰り返す直前の検索、一致の色付けを戻すこと（FR-138）は、`<CR>` で決めたときだけ行う。オペレーターの後の `/`（`d/foo`）でも同じく出す。ビジュアルモードの `/` では、画面を一致へ動かし、選択を一致の先頭まで広げて出し、一致には `incsearch` の色を付けない（Neovim 0.12.5 と同じ）。打つたびの検索には、エディタ全体の設定 `search.incrementalTimeoutMs`（整数。既定は 500、範囲は 1 から 10000）のミリ秒の時間の上限を付け、超えたらその回は一致を出さない。打つたびの検索は打つ手を止めない形で行い、前に打った分の結果が後から届いたら捨てる。`<CR>` で決めたときの検索には上限を付けない。マクロとドットリピートの再生の中では打つたびの検索を行わず、`<CR>` を押したときと同じ結果にする。打つたびの検索を行わない設定は持たない |
| FR-157 | 見た目の行（長い行を折り返した画面の 1 行。FR-156）で 1 行ずつ上下に動く操作（Vim の `gj` と `gk`）を、ID を持つ本体の操作として持つ（FR-126）。回数、オペレーターの後、ビジュアルモードで使える。動きとオペレーターの範囲（文字単位）は Neovim 0.12.5 の既定の `gj` と `gk` に合わせる。行を折り返さないときは、`j` と `k` と同じに動く。既定の `j` と `k` は、折り返していても実際の 1 行ずつ動く |
| FR-169 | 行のコメントを切り替えるオペレーター（Neovim の `gc`）と、カーソルの行を含む続くコメントの行を選ぶテキストオブジェクト（オペレーターの後の `gc`）を持つ。範囲の行が空白だけの行を除いてすべてコメントなら外し、そうでなければすべての行をコメントにする。記号を置く列、空の行と空白だけの行の扱い、外し方、回数、ドットリピート、アンドゥ、カーソルの位置は Neovim 0.12.5 の組み込みの `gc` に合わせる。既定のキーは、ノーマルモードとビジュアルモードの `gc`、ノーマルモードの `gcc`（行。回数は行数）、オペレーターの後の `gc`、ノーマルモードとビジュアルモードの `<C-_>` と `<C-/>`（ノーマルモードでは `gcc`、ビジュアルモードでは `gc`）とし、どれも操作の ID を持たせて `keymap` で割り当てを変えられるようにする（FR-126）。コメントの形は、バッファごとの設定 `comment.string`（文字列。Vim の `'commentstring'`。`%s` の前と後ろが記号になる。既定は空。空でなければ `%s` を含む）で決め、`:set` は `commentstring`（`cms`）を受け付ける。本体のファイルの種類ごとの既定（FR-163）に、本体が判定するファイルの種類と `lua` のコメントの形を Neovim 0.12.5 の ftplugin から写して持つ。形が空のときの `gc` は Neovim と同じく知らせて続ける |
| FR-173 | Vim のスクロールのキーを、ID を持つ本体の操作として持つ（FR-126）。`<C-e>` と `<C-y>`（表示領域を回数の行だけ送る）、`<C-d>` と `<C-u>`（表示領域とカーソルを Vim の `'scroll'` の行数だけ送る。回数を付けると `'scroll'` を回数にし、表示領域の行数が変わるまで保つ）、`<C-f>` と `<C-b>`（回数の画面だけ送る。`<PageDown>` と `<PageUp>` と同じ操作）、`zt`、`zz`、`zb`（カーソルの行を表示領域の上の端、中ほど、下の端に置く。回数を付けるとその行へ移る）、`z<CR>`、`z.`、`z-`（`zt`、`zz`、`zb` の後に行の最初の空白でない文字へ移る）である。ノーマルモードとビジュアルモードで使え、オペレーターの後では誤りにする。動き（表示領域の位置、カーソルの行と列、回数、バッファの端で動けないときの失敗、カーソルが表示領域から出るときの動き、行を折り返すときに見た目の行で数えること、ビジュアルモードの選択）は Neovim 0.12.5 の既定（`'nostartofline'`、`'smoothscroll'` はオフ）に合わせる。スクロールの量の数え方は、余白（FR-174）とカーソルを表示領域に入れる描画と共有し、キーごとに分けない |

FR-144〜FR-146 は、2026-11-20 のオーナーとの相談（#280）による。
オーナーの nvim は `U` を `<C-r>` に、`Y` を `y$` に割り当てている。
`J` と `K` を例外にするのは、Vim に慣れた人がよく使い、方針どおりに直すと、行をつなげる操作とホバーの置き場所を別に作る必要があるためである。
FR-145 と FR-146 は Vim と違う（Vim の `U` は最後に変えた 1 行の変更をまとめて戻し、`Y` は `yy` と同じ。[Vim との違い](vim-differences.md)）。
Vim の `U` に当たる操作は本体に無いので、`U` をリドゥにしても失う機能は無い。
Neovim 0.12.5 は、既定で `Y` を `y$` に割り当てている（同梱の文書の `:help Y-default`）。
FR-153 は、2026-11-20 のオーナーとの相談（#296）による。
Vim の `'incsearch'` に当たり、設定の項目を作らずに常に行う。
Neovim 0.12.5 は既定で `'incsearch'` がオンで、Vim 9.1 は本体の既定ではオフだが、設定ファイルが無いときに読む `defaults.vim` がオンにする（[Vim との違い](vim-differences.md)）。
見せ方は Neovim 0.12.5 に合わせた。時間の上限の既定は、Vim 9.1 の `'incsearch'` が検索を約 0.5 秒で打ち切る（`:help 'incsearch'`）のに合わせた。
`:s` と `:g` のパターンを打っている途中の見せ方（Neovim の `'inccommand'` など）は、FR-153 に含めない。
FR-157 は、2026-11-20 のオーナーとの相談（#300）による。
オーナーの nvim は `j` を `gj` に、`k` を `gk` に割り当てている。本体の既定の `j` と `k` は Vim と同じに保ち、オーナーは設定の `keymap` で割り当てる。
`$`、`0`、`^` は実際の行の端へ動く（Vim と同じ）。見た目の行の端へ動く `g$` と `g0` は持たない。
FR-169 は、2026-11-21 のオーナーとの相談（索引は #317。#327）による。
オーナーの nvim は、Neovim 0.10 から組み込まれた `gc` と `gcc` を使い、`<C-/>` と `<C-_>` をノーマルモードでは `gcc`、ビジュアルモードでは `gc` に割り当てている。
Vim 9.1 には既定の `gc` が無い（同梱の `comment` のパッケージを `:packadd` すると使える）ので、Neovim に合わせた。
1 つのファイルに複数の言語が入るもの（Markdown のコードの囲み）で、カーソルの位置の言語の記号を使う動き（Neovim は tree-sitter で決める）は、FR-169 に含めない。
FR-173 は、2026-11-21 のオーナーとの相談（索引は #317。#337）による。
PR #334 の再レビューで、本体のスクロールのキーが `<PageDown>` と `<PageUp>` だけで、[使い方](usage.md)がポップアップとプレビューで `<C-d>` が効くと書いていたことが分かったのが発端である。
`<PageDown>` と `<PageUp>` は、Neovim 0.12.5 の `nv_page` で `<C-f>` と `<C-b>` と同じ操作なので、同じ ID（`page-down`、`page-up`）にした。
#337 より前の `<PageDown>` と `<PageUp>` は Vim 9.1 の古いページ送り（`onepage`。`'startofline'` がオン）を写していたが、Neovim 0.12.5 の `pagescroll` に替えた。カーソルの列は、望みの列のままになる。
`G` と `gg` などの、Neovim の `'nostartofline'` で列を保つほかの操作は、FR-173 に含めない（今までどおり行の最初の空白でない文字へ移る）。

FR-190〜FR-192 は、2026-11-21 のオーナーとの相談（#317 の索引のインデントの 5 段目。#349）と、オーナーの方針「設定できるものは、すべて API から呼べるようにする」による。
#349 の issue が実装者に任せた点（拡張機能ごとに値を分けるか、エディタ全体の項目を変えられるか、拡張機能が止まったら外すか、今の値を読む口が要るか）は、#349 の実装で決めた（[基本設計](basic-design.md) 7.3 の「拡張機能から変えた値」）。

### 4.5 レジスターとマクロ

2026-11-18 のオーナーの裁定（#159）で、Vim のレジスターのうち直感に反する仕様を引き継がないことにした（1.1）。
この節の「履歴」は、レジスターの履歴（FR-51）を指す。

| ID | 要件 |
|---|---|
| FR-50 | レジスターの名前は、`a`〜`z`（`A`〜`Z` で指定すると追記する）、`_`（書いても何も残らず、読むと空）、名前の省略だけとする。それ以外の名前を指定した操作は失敗させ、メッセージを出す |
| FR-51 | レジスターの履歴を 1 本持ち、名前を省略したレジスター（無名のレジスター）は履歴の先頭と同じ内容にする。ヤンクと、名前を指定した書き込みは、書いた内容を履歴の先頭に積む。大文字の名前での追記は、追記した後の内容全体を積む。マクロの記録と、ビジュアルモードの貼り付けで置き換えられたテキストは積まない |
| FR-52 | 削除と変更で消したテキストを、履歴に積むかどうかを設定で指定できる。既定は積む。積まない設定では、削除と変更は無名のレジスターも変えない |
| FR-53 | 履歴の件数（既定 100）と、1 件あたりの最大の大きさ（既定 1 MiB）を設定で指定できる。最大の大きさを超えたテキストは履歴に積まずに無名のレジスターにだけ置き、積まなかったことをメッセージに出す |
| FR-54 | 履歴を一覧で表示し、選んだものを貼り付けられる |
| FR-55 | 貼り付けの直後に、貼ったテキストを、履歴の 1 つ前のものに置き換えられる。続けて使うと、さらに前のものに置き換える |
| FR-56 | 履歴の先頭が変わるたびに、その内容を OSC 52 の制御シーケンスで端末へ送り、ホストのクリップボードに入れる。送るかどうかを設定で指定でき、既定は送る。ホストのクリップボードは読まない |
| FR-57 | マクロの再生（`@a`、`@@`）をドットリピートの対象にする。`.` はレジスターの今の中身を再生し、再生の中で変更が起きたかどうかを問わない。マクロの中の `.` は、そのマクロの中の直前の変更を繰り返し、まだ変更が無ければ、再生を始める前の、マクロの再生ではない直前の変更を繰り返す。マクロの中の変更は、再生の外のドットリピートの対象を変えない |

FR-56 の注: 段階 3（8 章）では、端末を client ごとに持つので、送り先の端末を次のとおりに決める（仮。基本設計 4.5 の「段階 3 のレジスター」）。

| 履歴の先頭を変えた操作 | 送り先 |
|---|---|
| キーによる操作（ヤンク、削除、マクロの再生など） | その操作のキーを送った編集の client の端末。ポップアップとペインの部品の client で受けたキーは、元の編集の client（基本設計 1.2）の端末 |
| キーを伴わない変更（MCP や ACP など、拡張機能から本体への操作の結果） | 操作中の client（2 章）の端末 |

どの端末へ送っても、ホストのクリップボードに届くかどうかは、段階 2 までと同じく端末多重化ソフトの転送の設定（tmux の `set-clipboard`）で決まる。
端末多重化ソフトの外（FR-60）では端末は 1 つなので、送り先は変わらない。

### 4.6 段階 3 の要件の出どころ

4.7 から 4.14 は、段階 3（8 章）の要件である。

FR-112〜FR-122 と FR-124 は、#179 で、複数の振る舞いをまとめていた ID を分けたものである。中身は分ける前の ID と同じ裁定による。
FR-123 は、2026-11-18 のオーナーの裁定（#179 の 2 つのコメント）による。
FR-125 は、2026-11-19 のオーナーとの相談（#253）による。
FR-105 の書き直しと FR-147 は、2026-11-20 のオーナーとの相談（#286）による。
FR-149 は、2026-11-20 のオーナーとの相談（#288）による。
FR-152 は、2026-11-20 のオーナーとの相談（#295）による。
FR-148 と FR-159 は、2026-11-20 のオーナーとの相談（#308）による。
名前に「仮」と付けたもの（コマンドの名前、環境変数の名前、設定の項目の名前）は、実装の段階で変えてよい。

この節の要件の「client」は、次の 4 種類を区別する（基本設計 1.2）。

| 種類 | 内容 |
|---|---|
| 編集の client | ペインで起動した `vi-imitation` で、タブの行を持ち、バッファを編集する |
| ポップアップの部品の client | 中央のポップアップの中で、表示の部品だけを描く |
| ペインの部品の client | 本体が開いたペイン（ファイラ、DAP のペイン、ACP のペイン）の中で、表示の部品だけを描く |
| 待つだけの client | FR-83 で、渡したファイルのタブが閉じられるまで待つ。描かず、キーも受けない |

### 4.7 server と client

| ID | 要件 |
|---|---|
| FR-58 | 本体を server と client に分ける。server はバッファ、レジスターとその履歴、直前の検索、マクロ、ドットリピート、拡張機能を持ち、同じ server に繋いだ client の間で共有する。client は端末に描き、キーを受ける。例: ある編集の client でヤンクしたテキストを、同じ server の別の編集の client で貼れる |
| FR-59 | server は、tmux の window ごと、herdr のタブごとに 1 つとする。server のソケットのパスは、tmux のサーバーのソケットのパスと window の ID、または herdr のタブの ID から決める。同じ window（タブ）の中で起動した `vi-imitation` は、新しい server を作らずに、その server に client として繋ぐ |
| FR-60 | tmux と herdr の外で起動した `vi-imitation` は、server と編集の client を 1 つのプロセスで動かす。このときも server のソケットは待ち受け、待つだけの client（FR-83）は繋げる |
| FR-61 | server は、最後の編集の client が終わったときに、残った部品の client を閉じてから終わる |
| FR-112 | ペインを別の window（タブ）へ動かした編集の client は、元の server に繋がったまま動き続ける |
| FR-62 | 各編集の client は 1 本のタブの行を持つ。1 つのバッファは、どれか 1 つの編集の client のタブになる（タブとバッファは 1 対 1）。FR-109 の画面に出さないバッファと、FR-110 のポップアップの写しは、どのタブにもならない |
| FR-63 | 別の編集の client のタブになっているファイルを開こうとしたら、新しく開かずに、その client のペインへフォーカスを移す |
| FR-64 | 隠れたバッファを持たない。タブを閉じたら、そのバッファも閉じる |
| FR-113 | `:e {ファイル}` は新しいタブで開く |
| FR-114 | 編集の client の最後のタブを閉じたら、その client が終わる |
| FR-124 | `:qa` は、その client のタブだけを閉じる |
| FR-109 | 拡張機能が、どのタブにもなっていないファイルを編集するとき（ACP の `fs/write_text_file`、MCP の `open_file` で開いたファイルの編集、LSP の複数のファイルにまたがる名前の変更）は、タブを増やさず、画面に出さないバッファで編集を適用し、保存してすぐ閉じる。変えたファイルの一覧をメッセージの行に出す |
| FR-65 | client の中のタブの並びを、利用者が変えられる |
| FR-66 | server が端末多重化ソフトを操作する層を持ち、tmux と herdr のそれぞれで、ペインの分割、ポップアップを開くこと、フォーカスの移動を行う |
| FR-115 | 拡張機能は端末多重化ソフトを直接操作せず、本体に「ペインを開いて」「ポップアップを開いて」と頼む。本体は開いたペインかポップアップの中で、表示の部品を描く client を動かす |
| FR-67 | 画面の中央のポップアップは、tmux では `display-popup` で、herdr では本体が同梱する herdr のプラグインのポップアップのペインで開く。どちらも使えない（端末多重化ソフトの外など）ときは、client が自分のペインの中央に描く |
| FR-123 | 端末多重化ソフトの外（FR-60）では、ペインに出すもの（ACP の返答と進み具合（FR-111）、DAP のデバッグの情報とデバッグ対象の出力（FR-108）、ツリー型のファイラ（FR-105））を、ペインに代えて、編集の client の画面の中央のポップアップ（FR-67 の client が自分のペインの中央に描くもの）に出す |
| FR-147 | 拡張機能は、表示の部品を開くときに、端末多重化ソフトで分割したペインに出すか、画面の中央のポップアップに出すかを選べる。中央のポップアップに出したものは、項目を選んだら閉じられる。どちらの指定も、ファイラ（FR-105）に限らず、DAP（FR-108）と ACP（FR-111）のペインにも使える |

FR-123 の注: 2026-11-18 の裁定（#179 のコメント）は、ACP の返答と DAP のデバッグ対象の出力を決めた。
DAP のデバッグの情報（変数、スタックなど）のペインとファイラは、PR #180 の裁定要に答えた同じ日の追加の裁定（#179 のコメント）で、同じ扱いに決まった。
閉じたポップアップを開き直す手段は基本設計 1.2 にある。

FR-147 は、2026-11-20 のオーナーとの相談（#286）による。
ファイラの `<leader>e`（中央のポップアップ）と `<leader>E`（分割したペイン）を、ファイラのためだけの処理にせず、ペインを開く拡張機能に共通の指定で作るためである。
中央のポップアップに出したものを選んだら閉じるのは、中央のポップアップが開いている間それだけを操作する（FR-68）ので、選んだ結果（開いたファイル）が下に隠れるためである。
分割したペインに出したものは、選んでも閉じない。

### 4.8 ポップアップと表示の部品

FR-149 は、2026-11-20 のオーナーとの相談（#288）による。
幅の決め方は、オーナーの nvim の fzf-lua（窓は画面の 90%、プレビューは `flex` で、窓の幅が `flip_columns` の 100 を超えれば右に 60%）にそろえた。
ただし、狭いときに縦に並べることはせず、プレビューを出さない（オーナーの要望が「幅が十分にあれば右に」のため）。
一覧ごとにプレビューに出すものは、次のとおりに決めた。

| 一覧 | プレビューに出すもの |
|---|---|
| ファイル（`finder.files`）、ファイラのファイル | ファイルの先頭から |
| grep の結果（`finder.grep`、`finder.grepDir`、`finder.grepWord`）、行（`finder.lines`）、ジャンプリスト（`finder.jumps`） | そのファイルの、その行を真ん中にした範囲。その行に色を付ける |

ファインダーとファイラの専用の処理にせず、拡張機能が項目ごとに出すものを付け、本体が描く汎用の口にした。

FR-159 は、2026-11-20 のオーナーとの相談（#308）による。

ファインダーとファイラのためだけの処理にせず、プレビューを出すポップアップの中で効く汎用の操作にした（オーナーの方針）。

FR-152 は、2026-11-20 のオーナーとの相談（#295）による。

FR-171 は、2026-11-21 のオーナーとの相談（索引は #317。#329）による。
オーナーの nvim の `CursorHold` の自動コマンドで開く `vim.diagnostic.open_float(nil, { focusable = false, scope = "line" })`（`updatetime=100`）を取り込むもので、診断もポップアップも本体が持つので本体で作る（オーナーの決め）。
本体の既定は Vim の既定に合わせて出さず、オーナーの値（出す、100 ミリ秒）は同梱の設定の例（`config.example.jsonc`）に書く。
時間を待つ仕組みは、ポップアップのためだけのタイマーにせず、カーソルが止まってから時間が経ったことを知らせる汎用の契機（Vim の `CursorHold` と `CursorHoldI` に当たる）として作る（#329 の決め）。
#329 の決めは「表示の変化を拡張機能に知らせる口（#317 の第 3 弾）が同じ契機を使えるようにする」としていたが、PR #333 のレビューの裁定要へのオーケストレータの決定で、表示の変化の知らせはこの契機に載せず、Neovim の `CursorMoved` と `WinScrolled` に当たる別の契機（変化のたびに間引いて送る）にすると読み替えた。
止まってから時間が経ったら動くものだけが、この契機と時間（`cursorHold.delayMs`）を共有する。
このため、時間の設定は診断の下に置かず、契機の設定 `cursorHold.delayMs` にした（issue の案の `diagnostic.popupDelayMs` から #329 の実装で改めた）。
Neovim 0.12.5 との違い（コードを 2 回出さない、窓の幅の上限、閉じる契機）は、[基本設計](basic-design.md) 6.7 の「診断のポップアップ」にある。

FR-178 と FR-179 は、2026-11-21 のオーナーとの相談（索引は #317。#340）による。
オーナーの nvim の fidget.nvim（言語サーバーの `$/progress` を画面の右下に重ねて出し、終わると消す）を取り込むもので、表示は本体の知らせの欄に、送信は拡張機能からの通知（`progress/report`）にした（#317 の決め）。
Vim と Neovim に対応する既定は無い。本体の既定は出すにした（#340 の実装の決め）。
#340 より前の標準の拡張機能は、同じ進み具合（tree-sitter のパーサの用意、mise での言語サーバーの入れ込み。FR-142、FR-143）をメッセージの行に出していて、#340 でこの表示に替えたので、既定で出さないと、既定の設定のままの利用者から進み具合が見えなくなるためである。
終わったものを出しておく時間の既定（3000 ミリ秒）と、色と印の割り当ては、fidget.nvim の既定（`done_ttl` の 3 秒、表題の `WarningMsg` と `Constant`）に合わせた（2026-11-21 に、オーナーの手元の fidget.nvim のコミット 9e0201673e08e997e7cf52afca5565c70bd117f3 の `lua/fidget/progress/display.lua` で読んだ）。
回る印（fidget.nvim の `progress_icon` の既定）は、時間ごとに描き直す仕組みが要るので持たない。
出す client を 1 つにすること、失敗の印を分けること、待ちの間もその場で出すことは、PR #345 のレビュー（必須 1、推奨 1、推奨 2）による。
fidget.nvim は Neovim の画面の全体に 1 つだけ出し（既定の `relative = "editor"`）、end に成否の区別を持たない。
分割したペインの client のどれにも出すと同じ進み具合が 2 回出るので、拡張機能が後から届けるものの届け先と同じ考え方（[基本設計](basic-design.md) 1.2 の「その拡張機能へ問い合わせを始めた client に出す」）で 1 つに決めた。
描く位置、ポップアップとの重なり、狭い端末での扱いは、[基本設計](basic-design.md) 6.7 の「進み具合の表示」にある。

FR-235〜FR-239 は、2026-11-21 のオーナーとの相談（索引は #317）の第 3 弾の 3 本目（#369）による。
この上に、関数とクラスの見出しを窓の上端に固定する拡張機能（オーナーの nvim の nvim-treesitter-context。`max_lines = 4`、`multiline_threshold = 1`）と、カーソルを含むブロックの範囲の罫線を描き直す拡張機能（hlchunk.nvim）を、別の issue で作る。
知らせは、カーソルが止まった契機（FR-171）に載せず、Neovim の `WinScrolled` と `CursorMoved` に当たる別の契機にした（PR #333 のレビューの裁定要へのオーケストレータの決定）。
帯の下に隠れた行の扱い、帯の押し方、間引きの間隔、重なりの順は、2026-11-22 にオーナーの nvim に入っている nvim-treesitter-context（コミット 8decd73460d26ef0a0befb745d022dd1fc2c38b8）の `lua/treesitter-context.lua`、`lua/treesitter-context/context.lua`、`lua/treesitter-context/render.lua`、`lua/treesitter-context/config.lua` を読んで合わせた（[基本設計](basic-design.md) 6.7 の「窓の変化の知らせ」と「窓の上端の帯」）。
ポップアップの中のバッファを窓として知らせることは、#369 の範囲に入れていない。
FR-235 の横のスクロールの位置、FR-236 の拡張機能の側で古い知らせを捨てること、FR-237 の色の引き継ぎと古い帯を捨てることは、PR #376 のレビュー（必須 1、推奨 1、推奨 2）による。

ファイルの引数が `/` で終わるときに実行しないのは、オーナーの nvim の `<CR>` の割り当て（ファイルを開くコマンドの引数が `/` で終わるなら実行しない）と同じ考え方で、本体はコマンドの名前でなく補う語の種類（FR-195 のファイルを取るコマンド）で決める。
Vim の `'wildmode'` の `list`（一覧をメッセージの行に並べる）と `lastused`（バッファを使った順に並べる）は持たない。候補は常にポップアップの一覧に出し、バッファの候補は番号の順に並べる。
検索（`/`、`?`）の入力では補わず、`<Tab>` はタブ文字として入る。
#350 の issue は「Neovim は既定で補わない」としていたが、Neovim 0.12.5 は既定で `/fo<Tab>` をバッファの語で補う（2026-11-22 に `nvim --clean` で確かめた）。
本体のパターンは Go の正規表現の文法（FR-09）で、Neovim がパターンから語を作る規則がそのまま当てはまらないので、検索の補完は作らない（#350 の実装の決め）。
拡張機能のコマンドの引数を拡張機能に補わせる口は作っていない（#350 の実装の決め。拡張機能 API の版を上げずに済ませた）。
FR-199 の集めている間のキーの扱いと、FR-200 の `\` の扱いは、PR #353 のレビューの必須 1 と必須 2 による。
それまでは、集めている間に届いた補完のキーでないキーが集めるのを取り消してその場で働いたので、`:e alpi<Tab><CR>` をまとめて送ると補う前の `alpi` を開いた。
また、補った名前の `$` を `:e` がもう一度展開したので、`note$MYVAR.txt` を補うと `notesub.txt` を開いた。
値の無い環境変数と `~ユーザー名` を展開しないのは、`:w $NOPE/x` が根のディレクトリに書きに行かないためで、レビューの推奨 1 で Vim との違いとして残した。
`:colorscheme` と `:cd` に当たるコマンドは本体に無いので、補う対象に無い。

FR-215〜FR-217 は、2026-11-21 のオーナーとの相談（#317）で、コマンドラインと検索の入力をポップアップに出す表示を本体で作ると決めたことによる（#359）。
オーナーの nvim は noice.nvim の `cmdline = { view = "cmdline_popup" }` と `presets.command_palette = true` で、コマンドラインと候補の一覧を画面の上の中央に一体で出す。
本体の既定は Vim に合わせて最後の行に描き、オーナーの値は同梱の設定の例（`config.example.jsonc`）に書く。
オーナーの nvim は noice.nvim にメッセージを任せていない（`messages = { enabled = false }`）ので、本体も入力を終えた後のメッセージを最後の行に出す。
noice.nvim は入力の行の頭の `:`、`/`、`?` を隠して Nerd Font の印に置き換えるが、本体は入力の行に `:`、`/`、`?` を残し、前方と後方の検索を題の記号で見分ける（[基本設計](basic-design.md) 7.4 の「画面の上のポップアップ」）。

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | 最近の Linux ディストリビューションに、ファイルを置くだけで動作する。本体と拡張機能は別々のファイルとして配布する。本体と、tree-sitter 以外の標準の拡張機能は静的にリンクし、C の標準ライブラリの種類と版に依らずに動く。tree-sitter の拡張機能は glibc に動的にリンクするので、古い glibc（AlmaLinux 8 の 2.28 など）と musl（Alpine など）の環境では動かず、そこでは構文の色付けを使えない |
| NFR-02 | 本体は cgo を使わず、C の標準ライブラリに依存しない実行ファイルにする |
| NFR-03 | 拡張機能の異常終了が本体に波及しない。拡張機能のクラッシュ、panic、無限ループ、デッドロック、期限の超過、設定した上限の範囲でのメモリの使い切りが起きても、本体のプロセスは動き続け、編集中のバッファは失われない |
| NFR-04 | 拡張機能の読み込みは非同期とする。本体は、拡張機能の読み込みが終わるのを待たずに起動し、キー入力を受け付ける |
| NFR-05 | 軽量である。拡張機能なしで 10,000 行のテキストファイルを開いたとき、起動から文字を含む最初の画面を描き終えるまでが 20 ms 以内で、その後の本体の RSS が 16 MiB 以内である。`make build` が作る本体の実行ファイル（シンボルとデバッグ情報を削らない）が 12 MiB 以内である |
| NFR-06 | 利用者のマシンに、C コンパイラなどのビルド用の道具を要求しない |

NFR-06 の注: 拡張機能の管理（FR-102）で取得した拡張機能のビルドは、NFR-06 の範囲に含めない。
FR-102 は取得したソースを `go build` でビルドするので、その機能を使う利用者の環境には Go が要る。
2026-11-18 のオーナーの裁定（#177）で、このことを受け入れた。
FR-142 で取ってきたパーサのビルドも、NFR-06 の範囲に含めない。
FR-142 は取ってきたパーサの C のソースを C コンパイラでビルドするので、その機能を使う利用者の環境には git と C コンパイラが要る（tree-sitter の CLI は要らない）。
2026-11-20 のオーナーの裁定（#277）で、言語のパーサを利用する人なら C コンパイラがある前提にしてよいとした。
配布物の本体と標準の拡張機能は、引き続き Go と C コンパイラの無い環境で動く（基本設計 9.1 の `make dist-smoke`）。

NFR-01 の注: 2026-11-20 のオーナーの裁定（#277）で、このエディタは最近の Linux で動くことを目的とし、あらゆる環境で動くことは目的としないとした。
FR-142 のパーサを dlopen で読むために、tree-sitter の拡張機能を glibc に動的にリンクする（musl を静的にリンクした実行ファイルは dlopen を使えない）。
古い glibc と musl の環境では、構文の色付けをあきらめる。

NFR-05 の注: 本体の実行ファイルの大きさの上限は、2026-11-16 のオーナーの裁定で 10 MiB にし、2026-11-21 のオーナーの決めで 12 MiB に上げた（PR #310）。
PR #310（長い行の折り返し）で本体が 10 MiB をわずかに超えたことによる（2026-11-21 に main の 790934a の上へ載せ直した PR の本体は 10,497,446 バイトで、10 MiB を 11,686 バイト超えた）。
オーナーの言葉は「小さいのがベストだが、このサイズ以下でないとダメという上限値があるわけではない」である。
値はオーケストレータが決めた。上限は急な肥大に気づくための関門なので、今の大きさから 2 MiB ほどの余裕を置き、この先の機能の追加で毎回関門に当たらずに、数 MiB 単位の急な増加には気づけるようにした。

NFR-03 の注: 保証するのは、不具合のある拡張機能から本体を守ることである。
拡張機能は利用者と同じ権限で動く別のプロセスなので、悪意のある拡張機能がファイルを読み書きすることは防げない。

| 4 以降 | 未定 | - |

段階 1 で拡張機能のテキストオブジェクトを動かす理由は、キー入力ごとの RPC の応答時間が、この設計で最も不確かな点だからである。
Vim の標準の操作は本体が持つので、ノーマルモードだけを作っても RPC を通らない。
LSP の処理も大半が非同期なので、段階 2 でも確かめられない。
応答時間が実用にならないと分かった場合は、6 章の「拡張機能の実行方式」から見直す。

段階 1 で確かめることは、[段階 1 の計測](measurements/stage1-rpc-latency.md)で確かめた。
起動済みの拡張機能への往復は実用の範囲に収まったので、6 章の「拡張機能の実行方式」は見直さない。
段階 2 で確かめることは、`internal/exthost/stage2_test.go` の `TestStage2LSP` で確かめた。
このテストは、実際にビルドした `vi-imitation-ext-lsp` を起動し、強制終了の後の再起動で診断が戻ることを検証する。

段階 3 では、編集の状態を持つ server と、キーを受けて描く client が別のプロセスになる。
段階 2 までは、キー入力から画面の描き直しまでが 1 つのプロセスの中で済んでいたが、段階 3 ではキー入力ごとに client と server の間の往復が加わる。
このため、段階 1 の拡張機能への往復と同じく、client と server の往復の時間を最初に確かめる。
レジスター、マクロ、ドットリピートは、段階 2 まではエディタ全体で 1 つだった状態を、段階 3 では複数の client で共有するので、client をまたいだ使い方を確かめる。
判定の基準は 8.1 に書く。

段階 1 より後に検証する項目は次のとおりである。

- 拡張機能の起動が遅くても、本体の起動とキー入力が進む
- 拡張機能を強制終了しても、本体とバッファが残る
- 古いバージョン番号の編集が一度も適用されない
- 拡張機能が追加した操作を、ドットリピートとマクロで繰り返せる

### 8.1 段階 3 で確かめることの判定の基準

段階 3 で確かめること（この章の表）は、次の基準で判定する。
基準の値は、2026-11-18 のオーナーの裁定（#179 のコメント。PR #180 の裁定要に答えたもの）で決まった。
測り方のうち「仮」と書いたものは、実装の段階で変えてよい。
基準は、server と client を分ける最初の実装の issue の受入条件にする。
応答の計測は段階 1 の計測に合わせ、結果は `docs/measurements/` に、段階 1 と同じ節（結論、計測したもの、環境、手順、数値）で書く。

応答の計測は、次のとおりに行う。

| 項目 | 内容 |
|---|---|
| 比べる構成 | 1 つのプロセスの構成（FR-60）と、tmux の中と同じく server と編集の client を別のプロセスにしてソケットでつないだ構成（以後、分けた構成）。どちらも同じ実行ファイルで、拡張機能なし、利用者の設定なし |
| 分けた構成の起動 | tmux と herdr の外で起動すると 1 つのプロセスの構成になる（FR-60）ので、計測では、server だけを起動するオプションと、指定したソケットの server に編集の client として繋ぐオプションを使う（仮。名前は実装のときに決める。利用者向けの機能ではない）。このため tmux を通さず、tmux そのものの描画は計測に含めない |
| 測る区間 | 80 列 24 行の偽の端末（`make footprint-check` と同じ pty）にキーのバイト列を書いてから、その入力で変わった画面の内容が偽の端末から読めるまで。終わりは、操作ごとに決めた期待するバイト列（`j` は新しい行へカーソルを置く制御シーケンス、それ以外は変わった行の文字列）を読んだ時点とする（仮） |
| 操作 | 10,000 行のファイル（NFR-05 と同じ形）で、ノーマルモードの `j`、インサートモードでの 1 文字の入力、`dd`、`p`。分けた構成では、もう 1 つの編集の client で `yy` した直後に、測る client で `p` を打つ操作も測り、1 つのプロセスの構成の、同じ client での `yy` の直後の `p` と比べる |
| 間隔 | キーの前に 20 ms か 200 ms を置く（段階 1 と同じ。連続で送ると、待っている側が起きたままで短く出るため） |
| 回数 | 構成、操作、間隔の組み合わせごとに、最初の 20 回を捨てて 300 回。これを 3 回繰り返す |
| 統計 | p50、p99、最大。p99 は、段階 1 の計測のコード（`internal/exthost` の `TestStage1Latency` の集計）と同じく、n 回の値を昇順に並べた ⌈n × 99 / 100⌉ 番目とする。300 回では 297 番目（大きい方から 4 番目）である |

応答は、次の 2 つをどちらも 3 回の計測のすべてで満たせば、実用の範囲に収まったとする。

| 基準 | 値 | 根拠 |
|---|---|---|
| 分けたことによる遅れ | 操作と間隔の組み合わせごとに、分けた構成の p99 が、1 つのプロセスの構成の p99 に 1 ms を足した値以下 | 段階 1 の計測で、別のプロセスの拡張機能との往復は、間隔を置いて p99 が 0.68 ms 以下だった。client と server の往復も同じくプロセスの間の往復で、画面の更新のデータを運ぶ分を見込んで 1 ms とした |
| 分けた構成の最大 | 20 ms 以下 | 段階 1 の計測の、間隔を置いた往復の最大（2.1 ms 以下）の約 10 倍の余裕がある。段階 1 の計測が上限の根拠に引いた 0.1 秒（利用者が即座に反応したと感じる限界）の 5 分の 1 である。値は NFR-05 の、起動から最初の画面を描き終えるまでの上限にそろえた |

基準を満たさなければ、server から client へ送る画面の単位（基本設計 10 章の未決の項目）のもう一方の案で測り直す。
どちらの案でも満たさなければ、6 章の「本体のプロセスの分け方（段階 3）」をオーナーと見直す。

client をまたいだ使い方は、2 つの編集の client を 1 つの server に繋いだ結合のテストで確かめる。
次の表の操作の結果が、1 つのプロセスの構成で同じ操作をした結果と同じになれば良しとする。

| 対象 | 確かめる操作 |
|---|---|
| レジスター | client A でヤンクしたテキストを、client B で `p` で貼る。続けて `<C-p>`（FR-55）で、A で積んだ履歴の 1 つ前に置き換える |
| マクロ | client A で `qa` で記録したマクロを、client B で `@a` で再生する |
| ドットリピート | client A で変更した後に、client B で `.` を打つ |
| LSP | client A と client B のタブのファイルに、1 つの言語サーバーから診断とホバーが出る |
| DAP | client A で置いたブレークポイントで止まり、停止位置の印が、そのファイルをタブに持つ client に出る |
